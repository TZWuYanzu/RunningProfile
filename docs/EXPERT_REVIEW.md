## T-R1：历史训练精确检索方案

### 问题本质

用户可能在任意时刻问教练："上个月那次武功山的爬升训练你怎么评价的？"此时近 2-4 周的对话上下文里可能已经没有那次训练的信息。教练必须从归档数据中**精确召回**相关内容，而不是说"我不记得了"。

### 设计方案：结构化索引 + 语义检索双通道

```
用户提问
    │
    ▼
┌─────────────────────────────────┐
│        查询意图分类（LLM）        │
│  判断是否需要检索历史数据          │
│  输出：CURRENT（上下文足够）       │
│       / RETRIEVE（需要检索）      │
└──────────┬──────────────────────┘
           │ RETRIEVE
           ▼
┌─────────────────────────────────┐
│        查询改写（LLM）           │
│  "上个月武功山那次爬升训练"        │
│        ↓ 改写为                  │
│  结构化条件：                     │
│    date_range: [2026-05-01,      │
│                 2026-05-31]      │
│    location: "武功山"             │
│    type: "trail_run"             │
│    keywords: ["爬升"]            │
│  语义查询文本：                   │
│    "武功山越野跑爬升训练表现评价"   │
└──────┬──────────┬───────────────┘
       │          │
       ▼          ▼
  ┌─────────┐ ┌──────────────┐
  │结构化检索│ │ 语义向量检索   │
  │(SQL查询) │ │(Embedding)   │
  └────┬────┘ └──────┬───────┘
       │              │
       ▼              ▼
┌─────────────────────────────────┐
│         结果融合 + 排序           │
│  结构化命中 ∩ 语义命中 → 高置信   │
│  仅结构化命中 → 中置信            │
│  仅语义命中 → 低置信              │
└──────────┬──────────────────────┘
           │ Top-K 结果
           ▼
┌─────────────────────────────────┐
│     上下文组装 → 送入 LLM 回答    │
│  system prompt + 学员档案         │
│  + 检索到的历史活动摘要            │
│  + 检索到的教练点评                │
│  + 近期对话                       │
└─────────────────────────────────┘
```

### 可检索的数据源（4 个索引）

| 索引 | 数据来源 | 检索方式 | 示例查询 |
|------|---------|---------|---------|
| **活动索引** | `data.db` 中的活动记录 | SQL：按日期/地点/类型/距离/爬升筛选 | "5月份爬升超过1000m的训练" |
| **教练点评索引** | `training_notes` 表 | SQL（标签）+ 语义（note 内容 embedding） | "你之前说我下坡有问题的那次" |
| **学员档案** | `athlete_profile` 表 | 直接全量读取（数据量小） | "我的爬升能力评分是多少" |
| **归档对话索引** | `dialogue_timeline`（已归档） | 语义检索（对话摘要 embedding） | "上次我们讨论间歇训练的那次对话" |

### Phase 1 最小实现（不需要向量库）

Phase 1 数据量小（单用户、几百条活动记录），**不需要引入 embedding 和向量数据库**，用结构化检索即可覆盖 90% 的场景：

```python
# Phase 1 的检索实现：纯 SQL + LLM 查询改写
class SimpleRetriever:
    def retrieve(self, user_query: str, user_id: str):
        # Step 1: LLM 从自然语言提取结构化过滤条件
        filters = self.llm_extract_filters(user_query)
        # → {"date_after": "2026-05-01", "location_like": "武功山",
        #    "type": "trail_run"}

        # Step 2: SQL 查询活动记录
        activities = self.db.query_activities(user_id, **filters)

        # Step 3: 拉取这些活动对应的教练点评
        notes = self.db.get_notes_by_activity_ids(
            [a.id for a in activities]
        )

        # Step 4: 拉取时间范围内的归档对话摘要
        summaries = self.db.get_archived_summaries(
            user_id,
            date_range=(filters.get("date_after"),
                        filters.get("date_before"))
        )

        return RetrievalResult(activities, notes, summaries)
```

### Phase 2+ 升级路径

当数据量增长或用户提问更模糊时，追加语义检索通道：

| 阶段 | 方案 | 工具 | 触发条件 |
|------|------|------|---------|
| Phase 1 | 纯结构化 SQL 检索 | SQLite + LLM 查询改写 | 单用户、数据量 <1000 条 |
| Phase 2 | SQL + 本地 Embedding | SQLite FTS5 + `sentence-transformers` 本地模型 | 数据量增长、模糊查询增多 |
| Phase 3 | SQL + 向量数据库 | PostgreSQL + pgvector，或独立 Qdrant | 多用户、数据量 >10k |

### 关键设计决策

1. **检索作为 Tool 暴露给 LLM**：教练通过 function calling 调用 `search_history(query)` 工具，而不是每次对话都预检索。这与 T-S1（能力评估作为 Tool）的思路一致。
2. **活动记录必须带 location 字段**：当前 `data.db` 的活动数据需要确认是否有城市/地点信息。如果没有，需要在数据同步时通过 GPS 首尾点反向地理编码，提取地名后存储（GPS 坐标本身不存，只存地名）。
3. **教练点评是最重要的检索目标**：用户问的不是"那次跑了多远"（看历史 Tab 就行），而是"你当时怎么评价的"——所以 `training_notes` 的点评质量和可检索性是核心。

## T-R2：记忆固化 Staging 机制详解

### 什么是 Staging 区？

用一个生活类比：**staging 区就像教练的"草稿笔记本"**。

想象一位真人教练在和你聊完天后，先在自己的小本子上写下几条草稿——

> - "他说膝盖最近有点不舒服"（新增）
> - "之前记的'目标赛事是 UTMB'要改成'今年先跑 CCC'"（修改）

但他不会马上改到你的正式档案里。他先存着，回头确认一下这些理解对不对，再正式更新。

在系统中，这个"草稿笔记本"就是 staging 区——LLM 提炼出的档案变更**先存到一个临时表**，而不是直接覆写学员档案。

### 为什么需要 Staging？

| 场景 | 不用 staging（直接写入） | 用 staging |
|------|------------------------|------------|
| LLM 误解了用户意图 | 档案被错误覆盖，且无法追溯 | 变更待审核，可回滚 |
| LLM 遗漏了重要信息 | 丢失后无感知 | 可对比"本次对话内容 vs 提取结果"，发现遗漏 |
| 用户随口说了一句但不代表长期状态 | 被固化为"事实" | 可标记为"待确认"，不立即生效 |
| 需要调试固化效果 | 无日志可查 | 每次固化的输入/输出完整保留 |

### 完整流程

│                                      │

### 数据库表设计

```sql
-- 固化 staging 表
CREATE TABLE profile_staging (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id TEXT NOT NULL,
    op TEXT NOT NULL,              -- 'ADD' | 'UPDATE' | 'DELETE'
    field_name TEXT NOT NULL,      -- 对应 athlete_profile 的字段名
    old_value TEXT,                -- UPDATE/DELETE 时的旧值
    new_value TEXT,                -- ADD/UPDATE 时的新值
    reason TEXT,                   -- LLM 给出的变更理由
    source_dialogue_id INTEGER,    -- 关联触发此变更的对话 ID
    status TEXT DEFAULT 'pending', -- 'pending' | 'applied' | 'rejected'
    reviewed_at TEXT,
    created_at TEXT NOT NULL
);
```

### Phase 1 务实建议

Phase 1 用**模式 A（自动通过 + 审计日志）**即可。核心价值不在于让用户手动审批每条变更，而在于：

1. **可追溯**：每条档案变更都能回溯到"是哪次对话触发的"
2. **可回滚**：发现 LLM 提取错误时，按 `source_dialogue_id` 批量撤销
3. **可调试**：对比"对话原文 → LLM 提取结果 → 最终档案变化"，持续优化 consolidation prompt

## T-R3：多模型分层调用策略

### 设计原则

1. **成本优先**：日常对话用最便宜的模型，只在真正需要时升级
2. **大陆可用**：优先选择国产模型或有大陆合规接入渠道的模型
3. **人格一致性靠 Prompt，不靠模型**：教练的风格由 system prompt 保证，模型负责能力

### 三层模型路由

```
用户消息
    │
    ▼
┌─────────────────────────────────────┐
│          意图路由层（规则引擎）        │
│  根据消息内容 + 当前上下文分类         │
└──┬──────────────┬───────────────┬───┘
   │              │               │
   ▼              ▼               ▼
 日常对话      专业分析        复杂推理
 (Tier 1)     (Tier 2)       (Tier 3)
```

### 模型推荐与场景划分

| 层级 | 场景 | 推荐模型 | 备选 | 输入/输出定价参考 |
|------|------|---------|------|----------------|
| **Tier 1 · 日常对话** | 闲聊、简单问答、鼓励、确认计划、情绪回应 | **DeepSeek V3** | 豆包/通义千问-Turbo | ¥1/¥2 per 1M tokens（极低） |
| **Tier 2 · 专业分析** | 能力评估、训练数据解读、周总结、计划生成 | **DeepSeek R1** | Qwen-Max / GLM-4 | ¥4/¥16 per 1M tokens（中等） |
| **Tier 3 · 复杂推理** | 比赛策略生成、多赛事周期规划、伤病风险综合判断 | **Qwen-Max** 或 **GPT-4o**（如可用） | Claude 3.5 Sonnet（需代理） | ¥20-40/¥60 per 1M tokens |

> 注：定价为 2026 年 6 月参考值，国产模型价格战激烈，实际可能更低。

### 路由规则设计

```python
class ModelRouter:
    def route(self, message: str, context: DialogueContext) -> str:
        # Tier 3：复杂推理场景（显式触发）
        if context.active_tool in ["race_strategy", "season_plan"]:
            return "tier3"
        if self._mentions_race_strategy(message):
            return "tier3"

        # Tier 2：专业分析场景
        if context.active_tool in ["evaluate_ability", "weekly_summary",
                                    "generate_plan"]:
            return "tier2"
        if context.has_new_activity_data:  # 新同步了训练数据
            return "tier2"
        if self._asks_about_training(message):
            return "tier2"

        # Tier 1：默认日常对话
        return "tier1"

    # 路由规则用关键词 + 简单分类器，不用 LLM 判断（避免额外调用成本）
```

### 人格一致性保障

人格一致性**不依赖特定模型**，而是通过以下机制保证：

```
┌────────────────────────────────────────┐
│           System Prompt 架构            │
│                                        │
│  Layer 1：教练人设（所有层级共用）        │
│    "你是一位理性数据型跑步教练……"         │
│    风格指令 + 语气示例 + 禁止行为         │
│                                        │
│  Layer 2：学员档案（动态注入）            │
│    当前用户的能力评分、目标、偏好          │
│                                        │
│  Layer 3：场景指令（按 Tier 切换）        │
│    Tier 1："简短回应，不超过3句"          │
│    Tier 2："结合数据分析，给出依据"        │
│    Tier 3："深度推理，输出结构化报告"      │
│                                        │
│  Layer 4：Few-shot 示例（2-3 个）        │
│    确保不同模型输出风格一致               │
└────────────────────────────────────────┘
```

**关键点**：Layer 1（人设）和 Layer 4（示例）在所有 Tier 之间共享，这保证了不管用哪个模型，教练说话的感觉是一致的。区别只在于回答的深度和长度。

### 成本估算（单用户/月）

假设用户每天与教练对话 1-2 轮，每周有 4-5 次训练数据需要分析：

| 场景 | 频次/月 | 平均 tokens/次 | 模型 | 月成本 |
|------|--------|---------------|------|-------|
| 日常对话 | ~40 次 | ~2000 tokens | DeepSeek V3 | ≈ ¥0.24 |
| 训练分析 | ~20 次 | ~4000 tokens | DeepSeek R1 | ≈ ¥1.6 |
| 记忆固化 | ~20 次 | ~3000 tokens | DeepSeek V3 | ≈ ¥0.18 |
| 比赛策略 | ~2 次 | ~8000 tokens | Qwen-Max | ≈ ¥1.0 |
| **合计** | | | | **≈ ¥3/月** |

> 单用户月成本约 3 元人民币，远低于预期。即使用户量增长 10 倍，成本压力也很小。DeepSeek 的成本优势在这个场景下确实是决定性的。

### 关于 Claude 的务实建议

Claude 在长上下文和指令遵循上确实优秀，但考虑大陆合规现实：

- **Phase 1-2**：不接入 Claude，以 DeepSeek 系列为主力，Qwen-Max 做高端备选
- **海外版本**：如果后续做国际化，Claude / GPT-4o 作为海外用户的默认模型
- **Model Router 的抽象层依然要做厚**：即使现在只用 2-3 个模型，接口设计要支持未来扩展

## T-R4：SQLite 渐进式迁移路径

### SQLite 在各阶段面临的具体问题

| 阶段 | 数据规模 | SQLite 能力 | 瓶颈 |
|------|---------|------------|------|
| **Phase 1** | 单用户，<1000 条活动，<5000 条对话 | 完全够用 | 无 |
| **Phase 2** | 单用户，对话快速增长（日均 10-20 条），训练计划表新增 | 开始吃力 | 归档对话的全文检索变慢；写入和读取如果有并发（同步服务 + API 服务同时访问）可能锁冲突 |
| **Phase 3** | 多用户可能性，ITRA 赛事数据库（爬虫），对话量 >50k | 不适合 | 多用户并发写入；复杂查询（跨表 JOIN + 全文检索 + 聚合）性能差；缺乏连接池管理 |

### 迁移策略：不是"换数据库"，而是"分层卸载"

不需要在某个时间点把 SQLite 整体迁移到 PostgreSQL。更务实的做法是：**哪个能力不够了，就把那部分卸载到更合适的工具上**。

```
Phase 1                Phase 2                 Phase 3
─────────────────────────────────────────────────────────

SQLite (全部)    →     SQLite (核心数据)    →   PostgreSQL (核心数据)
                       + FTS5 (全文检索)         + pgvector (向量检索)
                       + WAL 模式 (并发读)       + 连接池

data.db (活动)   →     data.db 不动        →    迁入 PostgreSQL
                                                 或保持 SQLite 只读

                       对话归档 → 独立文件   →   对话归档 → PostgreSQL
                       (JSON/Parquet)            + 向量索引
```

### Phase 1：SQLite 即可，但要埋好接口

无需任何迁移动作，但代码层面做一件事——**用 Repository 模式封装所有数据库访问**：

```python
# 不要这样写（直接耦合 SQLite）
def get_notes(user_id):
    conn = sqlite3.connect("data.db")
    return conn.execute("SELECT * FROM training_notes WHERE user_id=?",
                        (user_id,))

# 要这样写（通过接口抽象）
class TrainingNotesRepository(Protocol):
    def get_by_user(self, user_id: str) -> list[TrainingNote]: ...
    def get_by_activity(self, activity_id: int) -> list[TrainingNote]: ...
    def create(self, note: TrainingNote) -> int: ...

class SQLiteTrainingNotesRepo:
    """Phase 1-2 实现"""
    def get_by_user(self, user_id: str) -> list[TrainingNote]:
        ...  # SQLite 查询

class PostgresTrainingNotesRepo:
    """Phase 3 实现，切换时只需改注入"""
    def get_by_user(self, user_id: str) -> list[TrainingNote]:
        ...  # PostgreSQL 查询
```

这样未来迁移时只需要写新的 Repository 实现，不需要改业务逻辑。

### Phase 2：三个低成本增强

**① 开启 WAL 模式（1 行代码）**

```python
# 解决：同步服务写入 + API 服务读取的并发冲突
conn.execute("PRAGMA journal_mode=WAL")
```

WAL（Write-Ahead Logging）让读写可以并发执行，解决 Phase 2 最大的痛点——数据同步进程和 FastAPI 服务同时访问 data.db 时的锁冲突。

**② 启用 FTS5 全文检索（增加 1 张虚拟表）**

```sql
-- 对话内容全文检索
CREATE VIRTUAL TABLE dialogue_fts USING fts5(
    content,
    content_rowid='id',
    tokenize='unicode61'  -- 支持中文分词
);

-- 查询示例
SELECT * FROM dialogue_fts WHERE dialogue_fts MATCH '武功山 爬升';
```

解决对话归档后的检索需求，不需要引入额外组件。

**③ 对话归档独立存储**

```python
# 超过 4 周的对话，摘要提炼后：
# - 摘要写入 dialogue_timeline（archived_summary 字段）
# - 原始对话导出为按月分割的 JSON 文件
#   archives/2026-05-dialogue.json
# - 原始记录从 SQLite 删除，控制主表体积
```

### Phase 3：评估是否需要 PostgreSQL

当以下任一条件触发时，考虑迁移核心数据到 PostgreSQL：

| 信号 | 具体指标 |
|------|---------|
| 多用户上线 | 同时活跃用户 > 10 |
| 写入并发 | 每秒写入 > 50 次 |
| 查询变慢 | 复杂查询（JOIN + 聚合）响应 > 500ms |
| 需要向量检索 | T-R1 方案升级到 embedding 检索 |

**迁移步骤**（如果触发）：

1. 部署 PostgreSQL（推荐用 Supabase 或 Railway 托管，省运维）
2. 安装 `pgvector` 扩展（向量检索）
3. 编写 `PostgresXxxRepo` 实现类
4. 数据迁移脚本：SQLite → PostgreSQL（`pgloader` 工具一键导入）
5. 切换 FastAPI 的依赖注入，指向新 Repository
6. 保留 `data.db` 的 SQLite 作为数据同步的本地缓存（同步脚本写 SQLite，后台 job 同步到 PostgreSQL）

### 决策建议总结

| 阶段 | 数据库 | 额外组件 | 改动量 |
|------|-------|---------|-------|
| Phase 1 | SQLite | 无 | 仅做 Repository 接口抽象 |
| Phase 2 | SQLite + WAL + FTS5 | 无 | 3 处小改动 |
| Phase 3 | 视信号决定是否迁移 PostgreSQL | pgvector（如需向量检索） | Repository 新实现 + 数据迁移 |

**核心原则：今天不为还没到来的规模付复杂度。** Phase 1 用 SQLite 完全正确，但通过 Repository 模式预留迁移能力，一旦需要，切换成本可控。
