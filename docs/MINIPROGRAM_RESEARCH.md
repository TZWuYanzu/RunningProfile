## 1. 核心产品调研

### 1.1 RQRun（RQ 跑力）

**产品概况**

| 维度 | 信息 |
|------|------|
| 开发者 | 厦门真跑科技有限公司 |
| 产品形态 | 微信小程序（核心）+ App（辅助） |
| 用户群体 | 马拉松/严肃跑者，用户量百万级 |
| 核心定位 | 数据驱动的跑步能力评估和训练指导 |

**核心功能：跑力值（RQ 值）**

RQ 跑力值是 RQRun 的核心差异化卖点，本质是一个综合反映跑者当前能力的指数。

与 VDOT 的对比：

| 维度 | Daniels VDOT | RQ 跑力值 |
|------|-------------|-----------|
| 数据来源 | 单次比赛成绩 | 近期训练数据 + 比赛成绩 + 心率 |
| 更新频率 | 静态（每次比赛后更新） | 动态（持续根据训练数据变化） |
| 考虑因素 | 最大摄氧量当量 | 训练负荷、恢复状态、跑步效率等多维度 |
| 数值范围 | 30-85 | 20-80 |
| 配速推算 | 5 区配速表 | 类似配速建议（基于 RQ 值） |

跑力值与马拉松成绩的大致对应：

| RQ 值 | 全马水平 |
|-------|---------|
| ~40 | 4:30-5:00 |
| ~50 | 3:30-4:00 |
| ~60+ | sub 3:00（精英业余） |

**训练计划功能**

- 基于跑力值和目标赛事自动生成训练计划
- 包含轻松跑、节奏跑、间歇跑、长距离等课型
- 配速基于 RQ 体系自动推算
- **局限：更多是基于算法/规则的模板化方案，非 AI 动态调整**
- 部分高级训练计划需要付费

**社交功能**

- **跑团**：创建/加入跑步社群，跑团内排行榜、打卡
- **榜单**：全国/地区跑力排行，按年龄性别分组，跑团间排名
- **跑友圈**：训练记录分享、动态互动
- 深度整合微信生态，分享非常便捷

**比赛服务**

- **成绩查询**：这是 RQRun 的强力功能。整合了大量国内马拉松赛事官方成绩数据，可查询自己和他人历史成绩
- **跑者档案**：汇总一个跑者的所有参赛记录
- **赛事日历**：国内马拉松赛事信息聚合
- **成绩预测**：基于跑力值预测 5K/10K/半马/全马成绩

**设备对接**

- 支持 Garmin、COROS、Suunto 等主流手表数据导入
- 可从手表训练数据自动推算跑力值

**商业模式**

- Freemium：基础功能（跑力值计算、成绩查询）免费
- 付费会员：详细训练分析、高级训练计划、深度跑力报告
- 其他：赛事合作（数据服务）、品牌广告、装备推荐导流

**用户评价**

| 正面 | 负面 |
|------|------|
| 跑力值体系直观易懂 | 算法不够透明，有时数值不合理 |
| 小程序形态轻便 | 训练计划模板化，不够个性化 |
| 成绩查询非常实用 | 部分功能需付费 |
| 榜单有激励作用 | 手表数据同步偶有问题 |
| 比赛数据库全面 | 数据导入不够及时 |

### 1.2 Run4Better（跑步向前）

**产品概况**

| 维度 | 信息 |
|------|------|
| 产品形态 | 微信小程序 |
| 用户群体 | 跑步爱好者，侧重训练提升 |
| 核心定位 | AI 教练 + 训练计划，已实现对话式 AI 教练 |

**AI 教练功能**

Run4Better 是国内较早在跑步小程序中引入 AI 教练概念的产品：

- 提供基于 AI 的训练建议和对话
- 可以根据用户跑步数据给出分析和建议
- 具备一定的个性化能力

**局限性分析**（基于小程序平台制约）：

| 维度 | Run4Better 的约束 | 我们的优势 |
|------|-------------------|-----------|
| AI 模型 | 受小程序计算和存储限制，AI 能力受制于平台 | 独立后端，可用高级 LLM（DeepSeek/Qwen） |
| 对话深度 | 小程序本地存储 10MB 限制，记忆深度有限 | 自建数据库，无限对话历史和持续记忆 |
| 数据接入 | 小程序蓝牙/传感器受限 | 通过 COROS API 完整同步 |
| 推送能力 | 仅微信订阅消息（需用户每次授权） | 可自由推送训练提醒/教练消息 |
| 后台运行 | 小程序后台约 5 分钟被挂起 | 服务端持续运行 |

**训练计划**

- 提供基于用户数据的训练计划生成
- 有一定的智能化程度
- 但受小程序平台制约，动态调整和实时反馈能力有限

**值得关注的点**

- **先发验证**：Run4Better 证明了"AI 教练 + 跑步"这个方向有市场需求
- **小程序天花板**：同时也暴露了小程序做 AI 教练的体验天花板
- **差异化空间**：对话深度、记忆持续性、数据完整性都是我们可以超越的维度

### 1.3 越野助手

**产品概况**

| 维度 | 信息 |
|------|------|
| 产品形态 | 微信小程序 |
| 用户群体 | 越野跑核心圈层，活跃用户数万级（垂直小众） |
| 核心定位 | 越野跑信息工具（赛事 + ITRA + 路线） |

**核心功能**

1. **ITRA 积分/成绩查询**
   - 国内最便捷的 ITRA Performance Index 查询入口
   - 解决了 ITRA 官网在国内访问不稳定的痛点
   - 不需要翻墙即可查询个人 PI 和赛事积分

2. **赛事查询与日历**
   - 国内越野赛事信息聚合
   - 赛事时间、地点、距离、爬升、报名链接
   - 赛事成绩和排名查询

3. **路线/GPX 查看**
   - 部分赛事提供路线轨迹预览

4. **社区/资讯**
   - 越野跑相关文章、赛事报道

**优势**

- 解决了一个非常具体的痛点（国内查 ITRA 积分）
- 无需下载，微信内即开即用
- 赛事信息在越野跑圈子有一定认知度

**劣势**

- 功能极其单一，本质是个信息查询工具
- 没有训练计划、数据分析等高价值功能
- 数据更新依赖人工维护，时效性不稳定
- 无法实现 GPS 轨迹记录
- UI/UX 相对简陋
- 天花板很低——"查一下就走"

**商业模式**

- 免费使用为主，可能通过赛事推广/广告获取少量收入
- 商业模式不清晰，变现困难

## 2. 其他跑步类小程序概览

### 2.1 大厂 App 的小程序延伸

| 小程序 | 母公司/App | 核心场景 | 独立价值 |
|--------|-----------|---------|---------|
| 悦跑圈小程序 | 悦跑圈（注册用户过亿） | 线上赛事、数据查看、跑团管理 | 低（导流工具） |
| 咕咚小程序 | 咕咚 | 赛事/商城入口 | 低（导流工具） |
| Keep 小程序 | Keep | 课程/内容浏览 | 低（导流工具） |
| COROS 小程序 | COROS | 营销活动/社区 | 低（设备管理在 App） |
| 佳明小程序 | Garmin | 社区/活动 | 低 |

共同特点：**所有大厂都把核心功能放在原生 App，小程序仅作为轻量入口和社交传播工具。** 这本身就是一个强烈信号——跑步场景的复杂性超出了小程序能力边界。

### 2.2 独立跑步/越野小程序（第二轮补充）

以下是第一轮未深入覆盖、但在跑步圈有一定用户基础的小程序：

#### 2.2.1 步道乐跑

| 维度 | 信息 |
|------|------|
| 定位 | 高校校园跑步打卡平台 |
| 用户量 | 数百万（主要是大学生，学校强制使用） |
| 核心场景 | 学校体育课要求的课外跑步任务：划定校园路线，GPS 校验，防作弊 |

- **亮点**：中国少有的"强制使用场景"的跑步小程序，DAU 极高（因为不跑扣体育分）
- **局限**：完全 To B（卖给学校），用户毕业即流失，和严肃跑者无交集
- **启示**：证明了"刚需 + 强制"才能保证小程序的高活跃，自愿场景下小程序的留存天然不行

#### 2.2.2 跑嗨乐 / 趣跑类

| 维度 | 信息 |
|------|------|
| 定位 | 线上赛事 + 社交跑步 |
| 核心场景 | 线上马拉松、虚拟赛事奖牌、跑步打卡 |

- **亮点**：虚拟赛事 + 实体奖牌模式在疫情期间一度火爆，抓住了跑者的"收集癖"和朋友圈晒图欲
- **局限**：疫情后线下赛事恢复，线上赛热度骤降；"发奖牌"模式的新鲜感消退后用户流失严重
- **启示**：纯虚拟激励（奖牌/证书）半衰期短，持续价值必须来自真实训练提升

#### 2.2.3 马拉松报名助手 / 跑步黄页

| 维度 | 信息 |
|------|------|
| 定位 | 赛事聚合 + 报名导流 |
| 核心场景 | 查赛事日历、比较报名费/赛道、一键跳转报名 |

- **亮点**：国内马拉松赛事信息极其分散（各赛事官网/公众号/微信群），信息聚合有真实需求
- **局限**：赛事信息维护靠人工采集，数据质量不稳定；报名环节无法闭环（最终跳转到各赛事官方）；赛季集中（春秋），淡季无流量
- **启示**：信息聚合类小程序天花板极低，无法形成用户习惯；但"赛事推荐"可以作为 AI 教练的能力之一

#### 2.2.4 跑步圈子 / 约跑类

| 维度 | 信息 |
|------|------|
| 定位 | LBS 约跑 + 跑团社交 |
| 核心场景 | 附近跑友、约跑活动发布、跑团活动管理 |

- **亮点**：尝试解决"一个人跑太无聊"的社交需求
- **局限**：跑步社交已经在微信群、Strava、悦跑圈中被充分满足；新建社交网络的冷启动极难；安全和隐私顾虑（LBS 约跑）
- **启示**：社交不是小程序能重新造的——微信本身就是社交平台，在微信上再造一个社交网络是悖论

#### 2.2.5 越野赛事类小程序（赛事方自建）

很多越野赛事方（如 UTCT、崇礼168、柴古唐斯、TNF100 等）会自建微信小程序或公众号：

- **功能**：报名、成绩查询、赛道 GPX 下载、领物通知、实时排名追踪（大型赛事）
- **亮点**：赛事期间 DAU 极高（选手+关注者的刚需）；实时排名追踪功能有不可替代性
- **局限**：赛后即弃用，典型的"阅后即焚"产品；每个赛事各建各的，无法复用
- **启示**：赛事信息 + 实时追踪是高价值但极低频的场景，适合被聚合而非独立存在

### 2.3 垂直工具类小程序

| 小程序 | 核心场景 | 特点 |
|--------|---------|------|
| 中国马拉松（田协官方） | 赛事报名/成绩查询 | 官方权威，刚需但功能极单一 |
| 各地马拉松官方小程序 | 报名/参赛信息 | 用完即走，无留存 |
| 最酷/去跑呗 | 跑团管理/打卡 | 轻量社交工具，数据靠手动输入 |
| ITRA/UTMB 查询类 | 积分查询 | 个人开发，维护不稳定 |
| 步道乐跑 | 高校跑步打卡 | 强制场景高 DAU，但与严肃跑者无关 |
| 马拉松报名助手 | 赛事聚合 | 信息靠人工维护，赛季外无流量 |

### 2.4 新兴 AI 类小程序

近年出现了一些尝试在小程序中做 AI 跑步教练的产品（如 Run4Better），但普遍面临：
- AI 能力受限于小程序平台
- 数据接入不完整
- 对话记忆和上下文管理困难
- 用户付费意愿低（"小程序 = 免费工具"的认知）

此外，2024-2025 年大模型热潮下出现了一些通用 AI 健身/跑步助手（非专门小程序，通常是公众号/H5/App 内嵌入的 ChatBot），但多数是套壳通用大模型，缺乏跑步领域的深度数据接入和专业性，停留在"问答机器人"阶段，无法做到：
- 读取用户的真实训练数据
- 基于生理学模型给出配速和周期化建议
- 持续跟踪训练执行情况和身体反馈

### 3.1 小程序生命周期分类（新增）

从用户行为角度看，跑步小程序可以按使用频次分为三类：

```
脉冲型（赛事驱动）  ────────────────────────────────────────
│  赛事报名/成绩/实时追踪      用户行为：赛前1周密集 → 赛后弃用
│  例：越野助手、马拉松官方     DAU 曲线：尖峰型，赛季外近乎归零
│
习惯型（日常训练）  ────────────────────────────────────────
│  训练记录/计划/数据分析       用户行为：需每天或每周打开
│  例：RQRun、Run4Better       DAU 曲线：相对平稳但绝对值不高
│  ⚠️ 这类场景小程序很难做好——需要后台运行、推送提醒、大数据存储
│
一次型（查完即走）  ────────────────────────────────────────
│  ITRA查分、赛事日历、配速计算  用户行为：有需要时来一次，无复访动力
│  例：越野助手(查ITRA)、配速计算器  DAU 曲线：极低且随机
```

**核心洞察：小程序的"用完即走"哲学恰好是跑步教练类产品的反面——教练需要的是"天天都在"。**

## 4. 为什么小程序没有成为跑步圈主流

### 4.1 技术硬伤：跑步场景与小程序能力的根本矛盾

**GPS/传感器：**
- 小程序 `wx.getLocation` 后台持续定位能力严格受限
- 2022 年起微信进一步收紧后台定位权限（需特殊资质审批）
- GPS 采样频率和精度远不如原生 App
- 无法直接访问加速度计、气压计（越野跑海拔数据关键）、心率传感器
- **结论：小程序无法作为可靠的跑步记录工具**

**后台运行：**
- 小程序在后台最多约 5 分钟被微信挂起
- 跑步活动 30 分钟到数小时，越野赛事 10-50+ 小时
- "保活"技巧（后台音频播放等）不稳定且违反平台规则
- **结论：长时间运动记录场景完全不可行**

**蓝牙/设备连接：**
- BLE API 存在但稳定性和兼容性远不如原生
- 连接 COROS/Garmin 手表、心率带、功率计体验差
- **结论：无法构建硬件设备生态**

### 4.2 数据能力不足

| 限制 | 影响 |
|------|------|
| 本地存储上限 10MB（单 key 1MB） | 复杂训练历史、GPX 轨迹文件超限 |
| 离线不可用 | 越野赛常在山区无信号 |
| 包大小限制（主包2MB，总包20MB） | 复杂功能/地图/图表难以实现 |
| 无后台数据同步 | 数据及时性差 |

### 4.3 用户体验天花板

- 地图组件功能有限，无法达到 Strava/COROS 级别的路线浏览
- 图表渲染性能差，训练数据可视化受限
- 无法实现沉浸式运动界面（锁屏显示、常亮屏幕）
- 切出微信可能丢失状态
- **"够用"但永远达不到"好用"**

### 4.4 推送与留存困境

- 仅支持微信订阅消息（需用户每次授权）
- 无法像原生 App 推送训练提醒、社交通知、赛事提醒
- 用户留存靠"主动打开"，缺乏被动召回能力
- **结果：用完即走 → 日活/周活低 → 难以建立使用习惯**

### 4.5 竞争格局已定

- **原生 App 生态成熟**：Strava/Keep/悦跑圈/咕咚已建立完整的数据-社交-内容-商业闭环
- **手表 App 是数据入口**：COROS/Garmin Connect 是运动数据的第一落脚点，习惯已形成
- **网络效应壁垒**：Strava 的全球社交网络、Keep 的国内内容生态，小程序无法复制
- **用户认知**："小程序 = 轻工具"，用户不愿在上面管理重要的个人运动数据

### 4.6 微信生态的双刃剑

| 优势 | 劣势 |
|------|------|
| 获客成本极低（微信全覆盖） | 用户数据归属模糊（平台 vs 开发者） |
| 社交分享天然融入聊天/朋友圈 | 平台政策风险（API 收紧、审核变严） |
| "用完即走"适合低频刚需场景 | 变现渠道受微信生态约束 |
| 开发成本低于原生双端 App | 高级功能实现受限 |

### 4.7 用户心智模型的错位（新增）

**跑步APP的用户信任迁移路径：**

```
手表记录数据 → 手表App查看 → 第三方平台深度分析 → 训练计划/教练
  COROS手表  →  COROS App  →  Strava/RQRun   →  TrainingPeaks/教练
```

在这条链路中，**信任是从硬件端逐级传递的**。用户信任 COROS 手表的数据精度 → 因此信任 COROS App → 因此愿意把数据同步到 Strava 做社交。

小程序的问题是：它试图在这条链路的中间插入，但既不掌握数据源头（硬件），也没有建立信任（"小程序 = 临时工具"的认知）。用户不会把核心训练数据托管给一个"用完即走"的产品。

**中国跑者的实际工具栈：**

| 场景 | 典型工具链 | 小程序位置 |
|------|-----------|----------|
| 训练记录 | COROS/Garmin 手表 → 手表 App | 无（不可替代） |
| 社交分享 | Strava / 悦跑圈 App → 朋友圈截图 | 边缘（转发工具） |
| 训练计划 | TrainingPeaks / 教练微信群 / 自己瞎练 | 几乎无 |
| 赛事信息 | 公众号 / 跑步群 / 越野助手查一下 | 偶尔（低频） |
| 装备购买 | 淘宝/京东 / 跑步群推荐 | 无 |
| 成绩查询 | RQRun 查一下 / 赛事官方 | 偶尔（低频） |

**关键发现：小程序在跑者工具栈中始终处于"偶尔用一下"的位置，从未占据过任何一个核心环节。**

### 4.8 变现困局：跑步小程序为什么赚不到钱（新增）

| 困局 | 解释 | 实例 |
|------|------|------|
| **用户付费意愿低** | "小程序 = 免费"是微信用户的默认心智 | RQRun 的付费会员转化率远低于同类 App |
| **广告场景差** | 跑步场景下用户停留时间短、注意力集中在数据上 | CPM 远低于内容/社交类小程序 |
| **电商导流弱** | 跑者装备决策周期长（一双跑鞋穿半年），不适合冲动消费 | 装备推荐转化率低 |
| **To B 天花板** | 赛事方合作收入有限且季节性强 | 越野助手的赛事合作收入难以覆盖运营成本 |
| **数据缺乏独占性** | 用户的训练数据在手表 App / Strava 都有，小程序没有不可替代的数据 | 用户随时可以不用，无迁移成本 |

对比 Keep 的变现路径（课程内容 → 会员 → 智能硬件 → 消费品），跑步小程序在每个环节都缺乏抓手。这不是产品能力问题，是小程序平台形态决定的。

### 4.9 总结：小程序的定位错配

**跑步场景的核心需求 vs 小程序能力：**

```
❌ 实时 GPS 记录（需后台持续运行）     → 小程序做不到
❌ 硬件设备同步（蓝牙稳定连接）       → 小程序勉强
❌ 海量数据存储（年度训练历史）        → 小程序受限
❌ 复杂数据可视化（心率图/配速图/海拔图）→ 小程序勉强
❌ 推送训练提醒（定时+触发式）         → 小程序受限
✅ 赛事信息查询（低频、轻量）          → 小程序适合
✅ 成绩查询/分享（社交驱动）           → 小程序适合
✅ 跑团管理/打卡（微信社交原生）       → 小程序适合
⚠️ AI 教练对话（需要后端但不需要硬件） → 小程序可行但体验受限
```

小程序天然适合"信息层"（查、看、分享），但跑步场景的核心价值在"数据层"（记录、分析、计划），这两者之间存在根本矛盾。

### 4.10 那为什么 RQRun 是最成功的？（新增）

RQRun 是所有跑步小程序中做得最好的，值得单独分析它"做对了什么"：

1. **发明了一个"社交货币"** — 跑力值不是最科学的能力指标，但它是最"可聊"的。跑者之间说"我跑力53"就像说"我考了630分"一样自然。VDOT、ITRA PI 都做不到这种口语化传播
2. **抓住了成绩查询的真空** — 国内马拉松成绩查询曾极其分散（每个赛事官网查），RQRun 做了聚合，成为"跑者简历"
3. **社交功能深度匹配微信** — 跑团、排行榜、分享卡片，所有设计都围绕微信社交链路
4. **不做记录，只做分析** — RQRun 明智地放弃了 GPS 记录（交给手表），只做数据的二次加工和社交包装

**RQRun 的天花板也很明显：**
- 训练计划是模板化的，无法根据个人状态动态调整
- 没有越野跑支持（跑力值体系不适用于越野场景）
- "跑力值"虽然有传播性但缺乏科学透明度，进阶跑者会质疑
- 变现主要靠会员+广告，ARPU 值低

## 5. 值得借鉴的功能与经验

### 5.1 RQRun 的成功要素

| 功能 | 为什么成功 | 我们如何借鉴 |
|------|-----------|------------|
| **跑力值体系** | 简单直观的能力量化，跑者间可比较 | 我们有 6 维能力评估，但需要一个"一句话可说"的综合分数（如类似跑力值的综合指标） |
| **成绩查询** | 解决实际痛点，高频使用 | 可考虑集成赛事成绩查询，增加用户粘性 |
| **跑团+榜单** | 社交激励驱动活跃度 | 社交功能是后期必须建设的。AI 教练 + 社交 = 更强粘性 |
| **跑力排行** | 竞技心理驱动，"我比别人强多少" | 可以做基于 ITRA PI 的越野跑排行（国内无人做） |
| **微信分享** | 传播成本为零 | Web App 也可通过微信内浏览器分享，但需要专门优化分享卡片 |

**关键洞察：RQRun 的跑力值虽然不如 VDOT 科学严谨，但胜在"可比较性"和"社交传播性"——跑者之间聊天说"我跑力值 52"比"我 VDOT 45"更自然。**

### 5.2 越野助手的成功要素

| 功能 | 为什么成功 | 我们如何借鉴 |
|------|-----------|------------|
| **ITRA 查询** | 国内独家痛点，免翻墙 | 应该内置 ITRA PI 查询和赛事级别评估 |
| **赛事日历** | 越野跑赛事信息分散，聚合有价值 | 可作为"教练Tab"中的赛事推荐功能 |
| **轻量即用** | 不需要注册/下载，查了就走 | 我们的 Web App 也应保证首次使用零摩擦 |

**关键洞察：越野助手虽然天花板低，但精准抓住了一个痛点。我们的 AI 教练如果也能查 ITRA 积分、推荐适合的赛事、分析赛道，就直接覆盖了越野助手的场景并远远超越。**

### 5.3 Run4Better 的先发教训

| 方面 | 观察 | 我们的应对 |
|------|------|-----------|
| **AI 教练方向正确** | 有市场需求，用户愿意尝试 | 证明了赛道可行性 |
| **小程序限制了 AI 深度** | 存储、计算、对话历史受限 | 我们用独立后端 + 高级 LLM |
| **持续记忆是差距** | 小程序做不到"教练记得你所有训练" | 我们的 3 层记忆系统是核心壁垒 |
| **用户付费意愿低** | "小程序 = 免费"认知根深蒂固 | 独立 App/Web App 用户付费意愿更高 |

### 5.4 跑团管理类的社交洞察

- 跑团是中国跑步文化的核心社交单元
- 微信群 + 小程序打卡是目前最常见的跑团管理方式
- **痛点**：数据靠手动输入/截图，无法自动从手表同步
- **机会**：如果 AI 教练 App 能同时服务跑团（团队训练计划、团队数据统计），是很强的获客渠道

### 5.5 步道乐跑的刚需验证

- 唯一一个 DAU 极高的跑步小程序——因为有"强制"场景
- **启示**：自愿场景下，小程序无法形成使用习惯；但如果教练能通过每日训练提醒创造"半强制"的节奏感（今天你需要做 X），就能提高打开率
- **反面教训**：步道乐跑虽然 DAU 高，但用户体验极差（学生普遍吐槽），说明"强制"不等于"好产品"，我们要做到用户"主动想打开"

### 5.6 线上赛事/虚拟奖牌的传播洞察

- 疫情期间虚拟赛事小程序爆发，核心驱动力是"朋友圈可晒"
- **启示**：跑者有强烈的成就展示需求。我们的训练报告/能力评估如果设计成"可分享的成就卡片"，自带传播属性
- **具体做法**：月度训练报告卡片、PB 庆祝卡片、越野赛完赛总结卡片——比虚拟奖牌更有实质内容

### 5.7 各产品做得好的"单点功能"汇总（新增）

| 功能 | 来源 | 做得好的原因 | 我们怎么做 | 优先级 |
|------|------|------------|-----------|--------|
| **ITRA PI 集成** | 越野助手 | 解决翻墙痛点 | 内置 ITRA PI 查询 + 教练解读，作为核心能力评估标准 | **P0** |
| **运动分享卡片** | Strava/digrun | 朋友圈传播，跑者有强烈晒图需求 | 在运动历史页生成分享图片，参考 Strava/digrun 的设计 | **P0** |
| **成绩档案** | RQRun | 一站式查所有马拉松成绩 | AI 教练引用成绩做趋势分析："你从去年半马 1:45 进步到 1:38..." | **P1** |
| **AI 对话** | Run4Better | 先发验证了需求存在 | 更深的记忆、更专业的训练学理论、更完整的数据接入 | **核心** |
| **训练打卡日历** | 跑团管理类 | 可视化连续性，激励习惯 | 训练日历 + 教练评价 = "教练在看你的执行情况" | **M4** |
| **跑力值/综合分数** | RQRun | 一个数字概括能力，可比较可传播 | 后续优化项，暂以 ITRA 分数为标准 | 保留 |
| **实时赛事追踪** | 赛事方小程序 | 赛事当天的刚需 | 保留项——用户比赛时累了看体感为主，看手机概率低 | 保留 |

## 6. 对我们产品的启示

### 6.1 产品形态选择

```
小程序      → 信息查询层（赛事、ITRA、分享卡片）
Web App     → 核心体验层（AI 教练、训练计划、数据分析）
原生 App    → 远期（如果需要实时 GPS 记录，但我们有 COROS 同步所以不急）
```

**推荐策略：Web App 为主体，小程序做轻量入口和社交传播。**

理由：
- Web App 无平台限制，可充分发挥 AI 教练能力
- 通过微信内浏览器打开 Web App，保留社交传播能力
- 不需要在 App Store 上架审核
- 与现有 running_page 技术栈一致
- 小程序可作为辅助：分享训练成绩卡片、查看简版数据

### 6.2 必须内置的"借鉴功能"

| 优先级 | 功能 | 来源 | 落地方式 | 决策备注 |
|--------|------|------|---------|---------|
| P0 | ITRA PI 集成 | 越野助手 | 教练能查询/预测 ITRA PI，作为核心能力评估标准 | 以 ITRA 分数为主要标准，不自创评价体系 |
| P0 | 配速/运动分享卡片 | Strava + digrun | 运动历史记录中生成精美分享图片，参考 Strava/digrun 的图片分享功能 | **用户强调非常重要**，在活动详情页实现 |
| P1 | 成绩查询/档案 | RQRun | 汇总用户所有参赛记录，教练可引用做趋势分析 | 已确认加入产品规划 |
| P1 | 赛事查询 | 越野助手 + RQRun | AI 教练可推荐适合用户能力的赛事 | — |
| P2 | 排行榜 | RQRun | 基于 ITRA PI 的越野跑排行（国内空白） | — |
| P2（保留） | 综合能力分数 | RQRun 跑力值 | 基于 6 维评估生成综合分数，可分享可比较 | 后续优化项，暂不自创评价体系 |
| P2（保留） | 实时赛事追踪 | 赛事方小程序 | 教练在赛中给实时策略建议 | 用户比赛时体感为主，看手机概率低 |
| P3 | 跑团支持 | 跑团管理小程序 | 远期功能，团队计划和数据统计 | — |

### 6.3 竞争差异化定位

```
┌──────────────────────────────────────────────────┐
│                 市场定位象限图                     │
│                                                  │
│   功能深度                                       │
│     ↑                                            │
│     │              TrainingPeaks                 │
│     │              (专业但贵)                     │
│     │                                            │
│     │                    ┌──────────┐             │
│     │                    │ 我们      │             │
│     │                    │ AI教练    │             │
│     │                    │ +越野专项  │             │
│     │                    └──────────┘             │
│     │    RQRun                                   │
│     │    (公路数据强)       COROS/Garmin           │
│     │                    (设备绑定)               │
│     │                                            │
│     │  Run4Better                                │
│     │  (AI尝试受限)                               │
│     │                                            │
│     │  越野助手                                   │
│     │  (信息查询)                                 │
│     │                                            │
│     └──────────────────────────────→ 易用性/获取成本│
│                                                  │
└──────────────────────────────────────────────────┘
```

**我们的独特定位：**

1. **唯一的越野跑 AI 教练** — 没有竞品能做到"基于 ITRA PI 目标 → AI 对话生成越野备赛计划"
2. **对话式调整 > 算法黑箱** — RQRun/COROS 的计划是黑箱生成的，用户只能接受或放弃；我们的教练会解释原因并通过对话调整
3. **持续记忆 > 每次重来** — 小程序的存储限制导致 AI 教练"金鱼记忆"，我们的 3 层记忆系统是结构性优势
4. **覆盖越野助手 + 超越 RQRun** — 内置 ITRA 查询 + 跑力值式的综合评分 + AI 教练 = 一站式解决

### 6.4 需要避免的小程序陷阱

| 陷阱 | 解释 | 应对 |
|------|------|------|
| 功能太轻 | 越野助手的"查一下就走"没有留存 | 核心价值是持续的教练关系，不是一次性工具 |
| 社交依赖 | RQRun 的排行榜在冷启动时没有吸引力 | 先做好单用户价值（AI教练），社交是增长手段不是核心 |
| 免费心态 | 小程序用户不愿付费 | Web App 定位为"教练服务"而非"工具"，用户为教练付费的意愿更高 |
| 数据不互通 | 各小程序数据孤岛 | 打通 COROS/Garmin 数据，做用户的"训练数据中枢" |

---

*本报告基于对 RQRun、Run4Better、越野助手等国内跑步小程序的调研分析。因网络限制，部分信息基于历史数据，建议实际体验各小程序获取最新状态。核心结论是：小程序适合做"信息层"但做不好"教练层"，这恰好是我们选择 Web App + 独立后端 + AI 教练定位的市场验证。*
